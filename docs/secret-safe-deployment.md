# Secret-Safe Deployment

This guide explains which values are safe to share and which must be kept private. Read this before deploying to testnet or mainnet.

---

## The Golden Rule

**Never commit a secret to the repository.**

Secrets include:

- Secret keys and seed phrases for any Stellar account (admin, verifier, deployer)
- Environment files that contain the above (`.env.docker`, `frontend/.env` with real IDs tied to funded accounts)
- Any value that grants unilateral control over a deployed contract

If a secret was ever committed, rotate it immediately — even if you deleted it in a later commit. Git history is permanent.

---

## What Is Safe to Share

| Value | Safe? | Notes |
|---|---|---|
| Contract IDs (C-prefix addresses) | ✅ Yes | Public on-chain. Safe to put in `README.md`, issues, or discussions. |
| Public key / Stellar address (G-prefix) | ✅ Yes | Public by design. |
| Network names (`testnet`, `mainnet`, `standalone`) | ✅ Yes | |
| RPC and Horizon URLs | ✅ Yes | Public endpoints. |
| WASM binaries | ✅ Yes | Compiled output; source is public. |
| IPFS hashes for documents | ✅ Yes | Content-addressed; safe to share. |
| `.env.example` and `.env.docker.example` | ✅ Yes | Template files with no real values. |

## What Must Stay Private

| Value | Private? | Notes |
|---|---|---|
| Secret key (`S`-prefix) or seed phrase | 🔴 Never share | Full account control. Compromise = loss of all assets and admin control. |
| `ADMIN_SECRET_KEY` in any `.env` file | 🔴 Never share | Used by deploy and admin scripts. |
| Hardware wallet PIN or mnemonic | 🔴 Never share | |
| Verifier key | 🔴 Never share | Can approve fraudulent KYC subjects. |
| `.env.docker` | 🔴 Never commit | Listed in `.gitignore`. |
| `frontend/.env` if it contains funded account keys | 🔴 Never commit | Listed in `.gitignore`. |

## Environment Files at a Glance

The repository mixes templates, checked-in public network configuration, and local files generated at deploy time. Use this table to decide what may be committed.

| File | Purpose | Category | Git status | May contain secrets? |
|---|---|---|---|---|
| `.env.docker.example` | Template for the Docker stack; copy to `.env.docker` | Example | Tracked | ❌ No — placeholders only (`ADMIN_SECRET_KEY=` stays empty) |
| `.env.docker` | Real Docker values, including `ADMIN_SECRET_KEY` | Local-only | Ignored | 🔴 Yes — never commit |
| `frontend/.env.example` | Template for frontend Vite variables | Example | Tracked | ❌ No — placeholders only |
| `frontend/.env` | Active frontend config written by `scripts/load-env.sh` or a deploy run | Local-only | Ignored | ⚠️ Treat as sensitive; never commit |
| `frontend/.env.bak` | Backup of `frontend/.env` created by `scripts/load-env.sh` | Local-only | Ignored | ⚠️ Same as `frontend/.env` |
| `frontend/.env.e2e.local` | Contract IDs generated by the E2E global setup | Local-only | Ignored | ❌ No, but regenerated per run — never commit |
| `services/event-indexer/.env.example` | Template for the event indexer service | Example | Tracked | ❌ No — local default database URL only |
| `env/local.env` | Public config for a local Stellar node (network name, RPC URL, empty contract IDs) | Checked-in public configuration | Tracked | ❌ No — public values only |
| `env/testnet.env` | Public Testnet config read by `scripts/load-env.sh testnet` | Checked-in public configuration | Tracked | ❌ No — public values only |
| `env/mainnet.env` | Public Mainnet config read by `scripts/load-env.sh mainnet` | Checked-in public configuration | Tracked | ❌ No — public values only |

Rules of thumb:

- **Example** files are templates. Copy them to their local-only counterpart and fill in values there; never put real values in the example file.
- **Local-only** files are listed in `.gitignore`. If `git status` ever shows one as staged, unstage it before committing.
- **Checked-in public configuration** (`env/*.env`) may hold only public values such as network names, RPC URLs, and contract IDs. Secret keys, seed phrases, and credentials must never be added to these files — inject them through environment variables or CI secrets instead.
- Real secrets do not belong in version control under any file name. If one is committed, rotate it immediately (see [Reporting an Accidental Exposure](#reporting-an-accidental-exposure)).

## Environment Variable Injection

All scripts and Docker services read secrets from environment variables rather than hard-coded values. This is by design.

### Local development (Docker)

```bash
# Copy the template — never edit the example file itself
cp .env.docker.example .env.docker

# Edit .env.docker — this file is gitignored
# Set ADMIN_SECRET_KEY to a throwaway testnet key only
nano .env.docker

# Start the stack — the .env.docker file is never mounted inside containers;
# Docker reads it at startup and passes the values as environment variables
docker compose --env-file .env.docker up
```

Never pass secret keys as command-line arguments. They appear in `ps`, shell history, and CI logs.

### CI

Store secrets in GitHub Actions repository secrets (`Settings → Secrets and variables → Actions`), not in workflow YAML files:

```yaml
# ✅ Correct — secret injected from repository secrets
- name: Deploy contracts
  env:
    ADMIN_SECRET_KEY: ${{ secrets.ADMIN_SECRET_KEY }}
  run: bash scripts/deploy.sh veritoken-ci
```

```yaml
# ❌ Wrong — secret visible in logs and git history
- name: Deploy contracts
  run: ADMIN_SECRET_KEY=SABC123... bash scripts/deploy.sh veritoken-ci
```

### Local non-Docker

```bash
# Export into the current shell session only — not persisted to .bashrc or history
export ADMIN_SECRET_KEY="SABC..."

bash scripts/deploy.sh veritoken-dev

# Unset after use
unset ADMIN_SECRET_KEY
```

To prevent the command from appearing in shell history, prefix it with a space (in bash with `HISTCONTROL=ignorespace`):

```bash
 export ADMIN_SECRET_KEY="SABC..."
```

## Shell History

Shell history is a common leak vector. Secret keys typed directly into the terminal can be recovered from `~/.bash_history` or `~/.zsh_history`.

Best practices:
- Use environment variable injection from files (see above) rather than inline values.
- After any accidental exposure, rotate the key and clear the history entry:
  ```bash
  history -d $(history | grep -n SECRET | tail -1 | awk '{print $1}')
  ```
- For production, use a hardware wallet or secrets manager so the raw key never touches the terminal at all.

## Placeholder Values in Documentation

All commands in `docs/mainnet-deployment.md`, `docs/incident-response.md`, and the `scripts/` directory use placeholder values for secrets. They look like:

```
<your-admin-keypair-name>
<ADMIN_ADDRESS>
G...VERIFIER_ADDRESS
SABC...  (never appears — use env vars)
```

These are intentional. Do not replace them with real values in documentation commits.

## Detecting Accidental Leaks

Before opening a pull request, scan staged changes for secret-like patterns:

```bash
# Simple grep for S-prefix Stellar secret keys (52-character base32 strings)
git diff --cached | grep -E '\bS[A-Z2-7]{55}\b'

# Or use a dedicated tool such as truffleHog or git-secrets
# https://github.com/trufflesecurity/trufflehog
# https://github.com/awslabs/git-secrets
```

If a secret is found:

1. Do **not** push.
2. Rotate the key immediately — treat it as compromised even if the diff is local.
3. Remove the secret from the staged change and re-stage.

## Reporting an Accidental Exposure

If a secret has already been pushed to a public repository:

1. Rotate the key immediately.
2. Follow the [Incident Response Runbook](incident-response.md) — specifically the Admin Key Rotation and Compromised Verifier sections as applicable.
3. Report the exposure via the [Security Policy](../SECURITY.md).

Do not open a public issue for a secret exposure.

## If a Deployment Credential May Have Been Exposed

A deployment credential is any key that deploys or administers contracts: the deployer key behind `TESTNET_DEPLOYER_SECRET` / `MAINNET_DEPLOYER_SECRET`, an `ADMIN_SECRET_KEY`, a Stellar CLI identity, or a verifier key. Treat a *possible* exposure (a leaked log, a lost laptop, a key pasted in chat) as a real one. This section points you to the first steps only. The [Incident Response Runbook](incident-response.md) is the canonical procedure.

**First steps, in order:**

1. **Stop using the credential.** Cancel any in-progress deploy workflows and do not run deploy or admin scripts with it.
2. **Contain on-chain impact if the key holds a contract role.** Use [Emergency Pause](incident-response.md#1-emergency-pause) if transfers may be at risk. For a verifier key, follow [Compromised Verifier Response](incident-response.md#3-compromised-verifier-response).
3. **Move contract admin roles to a new key** with the two-step handover in [Admin Key Rotation](incident-response.md#2-admin-key-rotation). Confirm every contract reports the new admin before you retire the old key.
4. **Retire the exposed key at the account level, using the network's supported account process.** A Stellar keypair cannot be changed in place. You either change the account's signers (add a new signer, then remove the old key's signing weight) or move to a new account. Follow Stellar's [signatures and multisig documentation](https://developers.stellar.org/docs/learn/fundamentals/transactions/signatures-multisig) for the network you deploy to. Veritoken does not provide its own key recovery mechanism.
5. **Replace every stored copy** with the new credential: GitHub Actions secrets (see GitHub's [using secrets in GitHub Actions](https://docs.github.com/en/actions/security-for-github-actions/security-guides/using-secrets-in-github-actions)), local `.env.docker` files, and Stellar CLI identities. If the old value was committed, deleting it does not make it safe (see GitHub's [removing sensitive data from a repository](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)). Rotation is still required.
6. **Report it privately** via the [Security Policy](../SECURITY.md).

Rotation stops future misuse. It does not reverse actions already taken with the exposed key. If the key may already have been used, for example if admin was transferred, approvals were issued or funds moved, escalate through the Security Policy and follow the runbook. Do not attempt a workaround.
